# 三省六部

把“以终为始”按需落到任务的责任边界和验收闸门上。三省负责守住三类底线，六部负责把七个既有节点做成可执行动作；不建第二套状态机。`implicit` 只做静默的事实、动作和终态检查，`light` 给出最小责任分工，`full` 才在正式七节点上展开完整 Gate。

## 三省职责

- **内容省**：守住事实基座。区分用户原始材料、权威数据、明确口述、派生结果、旧模板和调试记录；没有来源的内容标为假设、缺口或阻断输入。
- **行动省**：守住目标和动作。确认问题、受众动作、交付物、约束、节点顺序、技能/工具/模型、权限、回退点；只做已授权且属于当前节点的动作。
- **渲染省**：守住终态交付。检查格式、结构、可读性、渲染、路径、版本、清单和用户可用性；QA 未通过不得导出或宣称完成。

## 六部与七节点映射

这是现有 `route -> parse -> structure -> generate -> validate -> export -> review` 的责任叠加，不是第二套状态机。Host 状态中的 `governance` 是当前省、部和 Gate 的权威投影。

| 既有节点 | 责任省 | 执行部 | Gate 重点 |
| --- | --- | --- | --- |
| route | 行动省 | 澄清部 | 目标合同、受众动作、交付物、约束、验收和回退点完整 |
| parse | 内容省 | 搜寻部 | 真源、派生、调试和污染风险分开，关键输入可追溯 |
| structure | 行动省 | 规划部 | 结构能落到输入、输出、技能、工具、模型、QA 和回退 |
| generate | 行动省 | 执行部 | 只按已确认结构生成，保护上游和用户改动 |
| validate | 内容省 + 渲染省 | 检查部 | 事实、结构、格式、渲染和用户约束均有证据；失败阻断 |
| export | 渲染省 | 产出部 | 仅导出已通过 QA 的产物，记录路径、版本和交付清单 |
| review | 行动省 + 渲染省 | 检查部 + 产出部 | 逐项回读完成标准，分开报告实现、测试、实时验收和生产就绪 |

## 使用方式

1. 先加载 `goal-first-control` 并独立判断深度；只有模型选择 `light/full`，或路由为 `sop_required` 时，才把三省六部作为可见治理叠加，必要时再加载 `sop-orchestrator` 及领域技能。
2. 在每个 SOP 节点只声明当前省、当前部、Gate、证据和下一节点/回退点；不要用“体系化”“闭环”等空话替代具体责任。
3. 内容省的事实 Gate、行动省的授权/输入 Gate、渲染省的 QA/交付 Gate 任一未通过，都只能停在当前节点或回退到最早责任节点；不得用重试、降阈值或换模型掩盖缺口。
4. 失败时沿用 `reliable-development` 的证据优先恢复：冻结输入、版本、错误、运行态和产物，分类 failure fingerprint，只改变一个有效变量，保留已确认上游。

## 简单任务

`simple_direct` 不展示七节点、三省六部或其他仪式化流程，只做三个隐式检查：

1. **真源检查**：回答中的事实、范围和确定性是否来自用户输入或可核验来源；不把推断写成事实。
2. **行动检查**：是否只完成用户要求的动作，未擅自扩展范围、权限或交付物。
3. **终态检查**：是否满足用户明确的格式、数量、语言、长度、结果-only 和禁用内容要求；证据不足时如实说明限制。

## 完成判定

完成前回读 `goal_contract`：每项标记 `met`、`partial` 或 `not met`。实现、聚焦测试、全回归、实时用户流和生产就绪必须分开报告。任何 Gate 没有对应证据，都不能写成“已完成”。

当模型选择 `谋定后动=full`，或任务明确可复用/涉及虾缸运行时，再叠加 `plan-before-action`，保持会话状态与 Workflow 运行态分离。
