# 文体与语气路由

## 先确定四个变量

1. 谁读：本人、同事、领导、客户、公众、专业人员或系统用户。
2. 为什么读：了解、判断、批准、购买、执行、排错或继续对话。
3. 在哪里读：聊天、邮件、PPT、报告、网页、系统提示或研究记录。
4. 哪些内容不能改：事实、数据、状态、业务口径、术语或已确认原文。

## 聊天回复

- 先回答当前问题，不重复用户整段背景。
- 简单问题直接答；复杂问题说明判断、依据和下一步。
- 不用“首先、其次、最后”包装只有两三句话的回答。
- 不在每次回复结尾都总结、升华或主动追加无关任务。
- 技术内容只讲到帮助用户判断或行动的程度。

## 报告与方案

- 摘要只放关键判断和建议，正文补证据和解释。
- 每个结论能追到数据、材料或明确口述。
- 建议写清谁做、做什么、为什么、怎样验收。
- 正式不等于抽象。能说“客户可能不会买”，不写“采购意愿存在承压风险”。
- 不把计划、内部试跑或送审写成已交付。

## PPT与页面

- 一页一个主要判断。
- 标题表达本页结论，正文提供证据、解释或动作。
- 卡片标题、图表标签和注释各司其职，不重复同一句话。
- 字数受限时优先保留判断、对象和关键数字，先删修饰语和过程词。
- 需要详细规则时读取 `title-and-page-copy.md`。

## 分析与研究说明

- 分开观测结果、解释、假设和建议。
- 写清样本、时间、口径和限制。
- 相关性不能写成因果，模型分数不能换写成概率或承诺。
- 证据不足时明确说“目前只能说明什么”，不要用语气补足证据。
- 推荐、观察、试验和正式结论必须使用不同状态词。

## 产品与服务文案

- 先写用户遇到的问题，再写产品怎样解决。
- 把功能翻译成用户能感受到的变化，但不夸大效果。
- 行动提示写清点击后会发生什么。
- 不用行业黑话代替真实利益，也不制造焦虑逼迫用户决策。

## 系统提示与错误信息

- 第一行说明发生了什么。
- 第二步说明用户现在能做什么。
- 需要技术信息时放在后面，不让错误码成为主句。
- 不把系统责任推给用户，不用模糊的“操作失败，请重试”掩盖已知原因。

## 已锁定文本

- 不做整篇无痕重写。
- 逐项给出问题、替换句、理由和保持不变的事实。
- 不确定是否影响事实时保留原句并标记风险。
